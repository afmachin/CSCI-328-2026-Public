Cost and compatibility:
Sealing Student allows GraduateStudent because it is listed in permits,
but adding another direct subclass would require changing Student's
permits list. The three demonstration subclasses cannot compile under
this particular seal. Making Student final prevents all subclasses. It
cannot work with the current codebase because GraduateStudent already
extends Student.

Compiler checks:
With a sealed class, the compiler checks that direct subclasses are
permitted and that a permitted subclass is declared final, sealed, or
non-sealed. This check is useful if we deliberately want a closed set of
student subclasses. It does not check whether their methods keep
Student's behavioral promises.

RegistrationService and the needed stand-in:
RegistrationService.register asks Student for its ID to fetch grade rows
from LegacySisClient. It should check completed courses and prerequisites
using transcript data instead. If the transcript is loaded before
registration, register would not need to look up SIS grades using the
student ID. Student already holds a list of TranscriptEntry objects, so
that is where the student's transcript data belongs.

Sealing Student does not block the stand-in we actually need for this
external dependency. The service reaches into LegacySisClient for grade
rows. We could give the service a replaceable records-source interface,
using a fake source in tests and an SIS-backed source in production. That
fake would stand in for the records system, not for Student.
